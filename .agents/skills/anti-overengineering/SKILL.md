# 通用极简软件工程与防过度设计准则
> **适用范围**：跨越任何编程语言（Python, Go, Java, TypeScript, Rust, C++ 等）及任何架构层级（前端、后端、微服务、CLI、数据管道）。

本文档是针对 AI 编码助手（Codex / Cursor / Claude Code / Antigravity 等）制定的通用工程哲学与操作军规。
AI 模型的常见偏见包括：**不敢删除旧代码搞双轨并存**、**为了省 token 压缩代码**、**过度拆分微文件**以及**凭空臆想扩展性**。
任何 AI 助手在开发、重构或设计时，**必须死守以下五大基石原则**。

---

## 一、 五大通用基石原则（The 5 Universal Pillars）

### 1. 单一事实来源原则（Single Source of Truth, SSOT）—— 彻底拒绝双轨制与兼容胶水
- **核心思想**：系统中的任何状态、配置或执行链路，有且仅有一个权威源头（One Authoritative Source）。
- **AI 通病**：在接入新系统、持久层或真实实现时，AI 不敢废弃原有的 Mock/本地缓存/原型方案，而是自作聪明地搞“双模式并行”，并编写庞大的转换适配器（Adapters）、双向同步器、冲突决议器和状态锁。
- **通用红线**：
  - **新方案生效之时，即旧方案彻底删除之日**（In-place Replacement over Parallel Bridges）。
  - 严禁为了“兼顾过渡”编写双轨兼容胶水层。一旦引入权威数据链路，必须直接连接生产逻辑，彻底删除临时或模拟体系。

### 2. 直白叙事与意图展开（Explicit Narrative over Clever Density）—— 彻底拒绝高密压缩
- **核心思想**：代码是写给人读的，只是顺便能在机器上执行。代码的可读性、调试性永远高于字符密度。
- **AI 通病**：受 token 节约奖励或炫技本能驱动，把复杂的计算、数据过滤、异常处理塞在同一行；使用长链式流式调用（Chained Pipelines）；使用多层嵌套三元操作符或复杂单行推导式。
- **通用红线**：
  - **一行只表达一个逻辑意图（One Intent Per Line）**。
  - **展开中间状态**：将复杂的组合表达式拆解为具备清晰业务命名的中间变量，方便断点调试与日志追踪。
  - **平铺优于嵌套（Flat over Nested）**：大量采用卫语句（Guard Clauses / Early Return），杜绝深度缩进。
  - **意图级注释**：为非直观的业务分支和核心契约配齐简要注释，解释“为什么这样做（Why）”，而非重复代码在做什么（What）。

### 3. 行为就近与高内聚（Locality of Behavior, LoB）—— 彻底拒绝过度碎片化
- **核心思想**：理解一段业务逻辑所需跳转的文件数量，是衡量系统认知负担的核心指标。
- **AI 通病**：把 100 行清晰连贯的逻辑拆解为 8 个 15 行的微文件（Interface、DTO、Mapper、Validator、Helper、Utils、Constants、Index），并在每层目录做无意义的空转导出；任何调用都要穿越多层抽象。
- **通用红线**：
  - **行为就近原则（Locality of Behavior）**：仅由单一模块使用的辅助函数，直接内聚在该模块内部声明，严禁无故新建跨文件依赖。
  - **消除空转中转（Eliminate Indirection without Abstraction）**：没有真实多态需求时，不立空接口；没有跨域复用时，不立微文件。
  - **极简演进顺序**：遇到任何方案设计，严格遵循：**删除多余代码 > 复用已有机制 > 做出最小必要增量**。

### 4. 奥卡姆剃刀与现实验证（Occam's Razor & YAGNI）—— 彻底拒绝臆想模式与预先抽象
- **核心思想**：如无必要，勿增实体（Entities must not be multiplied beyond necessity）。只解决眼前明确的问题。
- **AI 通病**：需求只有一个确定流程，AI 却脑补出策略模式、工厂模式、观察者模式、动态插件网关、双模式选择器；为了“未来可能会变”凭空增加 5 倍的概念层。
- **通用红线**：
  - **严守 YAGNI（You Aren't Gonna Need It）**：绝不为推测性需求编写架构代码（No Speculative Generality）。
  - 需求要求一种确定解法，就以最直接、直白的方式实现；不要包装成需要用户配置、切换的复杂抽象框架。

### 5. 零遗留脚手架（Zero Lingering Scaffolding）—— 彻底拒绝临时代码转正
- **核心思想**：一次性代码留在生产代码库中，会迅速腐化为全团队的永久维护负担。
- **AI 通病**：临时编写的数据迁移接口、补丁转换器、原型界面、调试开关在任务结束后无人清理，后续迭代继续为其打补丁。
- **通用红线**：
  - 一次性数据转换、迁移脚本或临时原型，任务完成后必须**彻底物理删除**，不留任何遗留引用与影子逻辑。
  - 始终保持生产代码库处于“净室（Clean Slate）”状态。

## 二、 跨语言通用坏味道自查清单（Code Smells Checklist）

在提交或生成代码前，对照以下 6 项进行自查：
1. **是否存在胶水层？** 是不是有文件以 `*Adapter`、`*Bridge`、`*Sync` 命名，仅仅是在两个本该合二为一的模型间做搬运？（如果有，合并并删除其中一套）
2. **是否存在单行挤压？** 单行内是否塞了超过 2 级操作（比如 SQL 查询 + 过滤 + 映射全在 1 行）？（如果有，拆解成平铺语句并命名中间变量）
3. **是否存在空转微文件？** 是不是新建了小于 30 行的文件，且它只被一个地方调用？（如果有，直接内联合并）
4. **是否存在过度抽象？** 是否为了一个仅有单一实现的操作，声明了单独的 Interface/Class/Factory/Selector 结构？（如果有，直接使用具体函数）
5. **分支深度是否过大？** 是否存在大于 2 层的条件嵌套？（如果有，改用早期返回或卫语句展开）
6. **是否有临时残留？** 是否有一性次迁移数据、临时 mock 代码或历史兼容开关未删除？（如果有，彻底清理）

## 三、 任意 AI（Codex / Claude / Cursor）通用系统指令模板

你可以将以下这段纯文本指令，直接作为提示词（Prompt）放入任何 AI 的 System Prompt、`.cursorrules` 或任务前缀中：

```markdown
【通用极简软件工程红线（Universal Lean Engineering Rules）】
在任何语言与架构下编写代码时，必须严格遵守以下五条准则，坚决拒绝过度设计：

1. 唯一事实源头（拒绝双轨制）：
   - 严禁同时保留旧实现与新实现、或本地缓存与持久源双套逻辑。
   - 引入新方案时直接替换旧逻辑，严禁编写 Adapter、Bridge、双向同步锁等过渡胶水代码。

2. 直白可读（拒绝压缩代码）：
   - 一行只写一个逻辑意图；严禁长 SQL/高密流式链单行挤压与嵌套三元表达式。
   - 提取业务含义清晰的中间变量；优先使用卫语句（Guard Clauses）保持代码扁平。
   - 关键业务分支与核心契约必须附带中文意图注释，说明“为什么这样做”。

3. 就近内聚（拒绝文件碎片化）：
   - 辅助逻辑就近内联声明，严禁无故创建 <30 行的空转微文件或无逻辑的 barrel 导出文件。
   - 极简方案顺序：删除多余逻辑 > 复用已有机制 > 做出最小必要新增。

4. 奥卡姆剃刀（YAGNI 原则）：
   - 严格实现当下明确需求，严禁臆想未来扩展性；绝不自行设计多模式选择器、抽象工厂等冗余概念层。

5. 及时销毁脚手架：
   - 一次性迁移脚本、临时调试逻辑随任务终结必须立即删除，绝不留存在生产目录。
```
