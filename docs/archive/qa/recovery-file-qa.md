# 恢复文件导入验收

2026-10-09 02:35。完成实际工作副本下载、文件选择器导入、重复导入、无效文件及编辑器恢复的桌面路径。当前导入器只读取文件中已经登记的编辑暂存，不将整个工作空间直接覆盖回去，也不重放失败的发布、付款或其他业务操作。

## 实际路径

验收在独立的 5201 来源运行相同前端代码，使用其示例工作空间；5198 的用户工作空间没有参与此次修改。两个页面先后编辑示例表单名称与个人信息，触发真实的多页保存冲突。

1. 在未提交的个人信息中填写“恢复文件验收输入”。另一标签页保存表单名称后，原页出现“保留与恢复”。通过“下载工作副本”取得实际 JSON 文件。
2. 在另一个标签页的恢复对话框，通过系统文件选择器导入此文件：编辑暂存从 0 份变为 1 份，个人信息和业务数据没有自动保存。重复导入仍为 1 份。
3. 明确点击“暂存到此标签页”“放回当前编辑器”“确认放回”，姓名回到编辑器。当前页已有保存冲突，保存被拒绝而输入保留。刷新读取最新工作空间后，明确恢复并保存成功。
4. 再次打开工作台，头像菜单显示已保存的“恢复文件验收输入”，最新表单名称仍保留。再次导入原副本时，因为个人信息基线已经变化，恢复按钮被禁用，避免覆盖新的原配置。
5. 首次导入成功提示保持可见。随后导入无效文件显示具体错误，不残留前一次成功提示，已经读取的 1 份暂存保留。再导入原文件显示新增 0 份，错误清除。

工作副本：`output/qa/workspace-recovery-file.json`，169584 字节，SHA-256 为 `951917f2e54db92727998ca46d464d94902150136db7bcf214ccab9963ca08b4`。其中 1 份编辑暂存；验收示例工作空间为 10 个表单、0 条业务记录。无效样例为 `output/qa/invalid-recovery-file.json`。

## 修复及证据

`EditorDraftRecovery.vue` 在首次导入引起自动选中之后再设置结果提示，避免选中监听清空成功提示；每次文件或文本导入前清除旧反馈，避免错误与陈旧成功提示并存。

`frontend/tests/recovery-file.test.ts` 的 2 项组件测试覆盖真实组件与 Pinia 的导入路径、重复去重、仅保留内存、无效文件不破坏已有内容、15 MB 上限和超限不读取文件。当前全量前端 42 个文件、395 项通过；完整构建、4 项 Sites 检查及 4 个受保护文件哈希通过。
