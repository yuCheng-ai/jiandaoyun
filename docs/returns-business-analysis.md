# 退换货案例中的通用平台能力分析 草案

退换货需要同时跟踪退回数量、清点差异、检验处置、库存单据、损失核算和客户沟通。同一笔业务在数量未退齐时，已退部分可以继续处理，缺件部分另行沟通。因此，产品需要支持一笔业务中的多个独立任务及其汇合条件。

产品目标是通用业务设计平台。本案例用于发现可复用的建模和交互能力，并作为配置验收素材；下面的退换货记录、部门和职责均是业务配置示例。0725 版是否为最终确认版本、实际 ERP 及接口边界只影响企业配置定稿，不阻断通用平台能力设计。

## 通用能力与配置入口

| 平台能力 | 用户需要能配置什么 | 核心运行约束 |
| --- | --- | --- |
| 数据定义与表单视图分离 | 为相同业务数据配置不同填写、处理和查看页面；普通新建表单可自动创建对应数据定义 | 页面复用稳定字段 ID，界面布局不改变记录身份；组合页面按绑定定位实际记录 |
| 明确的数据关系 | 一对多、多对多、主从归属、关联引用、汇总计算，以及实时读取或保留快照 | 引用与复制有明确语义；删除、变更和历史版本的影响可检查 |
| 明细独立处理 | 选择要处理的关联记录或明细范围，为每条或每组创建任务 | 明细具有稳定身份，任务关联具体数据；整表、逐条和分组处理可选择 |
| 精确权限 | 角色或部门、记录范围、子表行范围、子字段、任务节点，以及新增删除等操作 | 服务端统一执行；布局显隐不授予权限；并发修改与结构变更有保护 |
| 流程独立于表单 | 为节点绑定现有记录、新建关联记录或一组明细；区分审批、填写、确认和自动操作 | 流程实例可以引用多种数据，支持多个活动任务，记录状态与任务状态分别维护 |
| 并行与汇合 | 并行任务、按明细生成任务、等待关联记录满足条件、全部或部分任务达标后继续 | 明确任务集合固定还是动态加入，定义超时、取消和异常后的汇合行为 |
| 业务动作与外部执行 | 在节点中选择创建、修改、关联、状态变更、通知或连接器动作，配置输入和输出 | 本地动作有权限及事务边界；外部动作单独记录执行结果并支持受控重试 |
| 运行总览与配置检查 | 配置业务总览展示哪些记录与进度；模拟身份、样本数据和失败路径 | 检查失效引用、权限冲突和可判定的等待问题，展示每一步实际读写和阻塞原因；不宣称能静态证明所有流程正确 |

常规入口仍围绕数据与关系、表单页面、流程设计展开，权限和动作在使用位置配置。高级能力逐步展开，简单的单表审批保留短路径。

平台发布版本应记录其依赖的数据定义、页面、流程和规则版本。运行中业务按明确的版本策略执行，调整配置不能无意改写已完成任务及其审批依据。

## 原图明确表达的业务

| 环节 | 原图内容 | 对产品的要求或待确认边界 |
| --- | --- | --- |
| 发起与责任说明 | 涉及销售部、大客户部及责任部门。已知责任由责任部门经办人签字；公司责任但部门不明时由质管办签字。淘宝退换货由合同执行部经办人直接发起 | 发起渠道、经办责任和审批角色需要分别建模；特殊渠道是否仍需销售签署待确认 |
| 签署 | 相关销售人员手签，驻外人员签字拍照；增加部长签署，无论是否有损失 | 签署内容及附件应对应当时版本；能否替换为系统签署需要业务确认 |
| 批准与交接 | 退货批准后制审退货单，原件流转仓库，复印件给质管办与财务备案 | 审批、实际制单和备案是不同动作；图中“退货单”“退货通知单”的实际系统含义待确认 |
| 清点差异 | 型号不符时区分客户原因和原始单据错误；涉及仓库、研发、合同执行和销售沟通 | 差异需关联具体物料，明确谁修正什么、何时恢复处理；清点数量不能被沟通结果无痕覆盖 |
| 数量未齐 | 缺件明细随复印件继续流转、与顾客沟通；已退部分随原件继续红字出库、调拨和检验 | 同一业务同时存在实物处理和缺件跟进两条进度；缺件不应自动阻断已退部分 |
| 检验和处置 | 检验包含包装情况，不合格拍照。质检主导、机械研发配合；报废、返工、拆卸由质检决定，返修和其他处理由机械研发决定 | 检验结论、处置决定、执行结果应分别记录；质检部与质管办不能合并成一个角色 |
| 执行单据 | 合格品走调拨；不合格分包装报废、拆卸、返工返修、报废或其他处理，涉及拆卸单、生产订单、损失清单、材料出库单 | 每项执行应保留关联物料、数量、单据和实际执行状态；同一物料能否拆分数量走不同处置尚待确认 |
| 核价与归档 | 0725 版由合同执行部与物料部参与核价，合同执行部填写运费。损失件有销售价按销售价，无销售价按成本价乘系数。后续质管办编制质量损失处理表，分管副总经理参与审批，质管办传递损失情况并归档 | 核价输入、计算依据、运费和审批快照应可追溯；图中未定义系数、费用分摊及完整结案规则 |

## 两版差异及其影响

| 位置 | 草案 | 0725 版 | 需要确认的决定 |
| --- | --- | --- | --- |
| 退货存放与库存 | 提出新增退换货滞留库，并说明挂原料库影响排产；制退货单旁注明选择原发货仓库 | 上述中部说明不再显示，但顶部仍保留不能先挂原料库的意见及仓库调拨意见 | 滞留库方案是取消、另行处理还是遗漏；仓库顺序及可用库存时点分别是什么 |
| 缺件分支 | 缺件明细与客户沟通 | 新增“处理意见抄送发起人”，旁注“自由项强制完成” | 自由项是必填字段、任务、ERP 字段还是其他含义；抄送与确认是否相同 |
| 价值核算 | 物料部 | 合同执行部、物料部；注明合同执行部填写运费 | 两部门可编辑内容、交接顺序、运费录入时点及核价完成条件 |
| 未退齐结案 | 图下部存在质管办判断是否完结、退不齐返回表，经合同执行和销售继续沟通的支线 | 该支线不再显示 | 是否被其他闭环替代；缺件如何补齐、核销或经批准豁免后结案 |

图形删除不能直接作为取消业务控制的依据。两版确认前，不把任一版的差异默认执行为正式规则。

## 通用数据模型在案例中的配置示意

配置此案例时，业务总览可以关联以下记录。记录名称均由业务配置提供；平台提供数据定义、记录、关系、明细和任务等通用机制。具体记录可以在同一页面以子表形式显示，其界面位置不决定数据是否具有独立身份。

| 记录 | 主要内容 | 关联方式 |
| --- | --- | --- |
| 退换货业务 | 客户、来源、经办人、责任说明、签署记录、整体进度 | 统一关联所有明细、任务与业务单据 |
| 申请明细与到货明细 | 原发货物料、申请数量、实际到货、批次或序列号（按物料规则确定） | 每条明细具有稳定 ID，到货关联申请明细，支持多次到货 |
| 差异跟进 | 少退、多退、错退、非本公司物料、原始单据错误及沟通结果 | 精确关联问题明细或到货记录，保留处理人与解决依据 |
| 检验与处置 | 检验数量、包装情况、照片、结论、处置类型、决定人 | 关联实际到货；处置数量的分拆、合并规则先确认再实现 |
| 执行记录 | 调拨、拆卸、返工返修、报废以及相关单据状态 | 关联处置及 ERP 单据 ID；协作任务完成与 ERP 执行成功分别记录 |
| 损失核算 | 损失件、价格依据、系数、运费、承担方及审批版本 | 关联实际处置和原始单据，避免重复计损 |
| 任务与历史 | 负责人、可处理范围、截止条件、阻塞原因、操作记录 | 任务可关联多张单据或指定明细，业务实例可以同时有多个活动任务 |

数量、检验、处置、库存执行、核价分别维护状态；整体进度由明确规则汇总。批准退货、实物到达、检验合格、ERP 入账和库存可用是不同状态，不相互替代。

涉及核价和签署的内容保存当时快照。其他关联信息是否实时读取，由字段用途决定，避免源数据变动无意改写已审批的内容。

## 通用权限在案例中的配置示意

| 角色 | 主要处理内容 | 权限原则 |
| --- | --- | --- |
| 销售和大客户部 | 客户信息、原因说明、客户沟通、相关签署 | 操作范围与经办关系、部门及任务共同决定 |
| 合同执行部 | 业务衔接、单据关联、缺件沟通交接、运费 | 运费与物料核价分别授权；能否修改核价结果待确认 |
| 仓库 | 到货清点、数量差异、仓库及调拨执行情况 | 不通过修改清点结果替代后续核销决定 |
| 质检部和研发 | 检验与各自负责的处置决定 | 按处置类型确定决定权，协作意见与最终决定分开 |
| 生产部 | 拆卸、返工返修等执行情况 | 操作实际分配任务对应的明细，不覆盖检验依据 |
| 物料部 | 损失物料核价及相关依据 | 核价输入独立于仓库数量和合同执行部运费 |
| 质管办和分管副总经理 | 损失处理、审批及归档 | 结案权、退回权和例外批准权按确认后的规则配置 |
| 财务 | 图中明确为备案接收方 | 其他财务操作权限不从备案职责推导 |

以上是待业务确认的权限分工，不是已获批准的权限矩阵。读取、提交、导出、打印、附件访问及历史查看都需要执行一致的服务端权限规则。

退换货总览显示已退、未退、待检、处置中和待核价的明细，以及阻塞原因和当前负责人。仓库、质检和合同执行部从自己的待办进入同一业务上下文，只修改被授权的列或记录。

明细变更按稳定行 ID 和字段 ID 提交。不同字段的并发修改应保留双方结果；相同字段或有关联约束的修改应检查版本、明确冲突。新增、删除、排序和拆分明细分别检查权限，不能将整张子表覆盖作为默认保存方式。

## 企业配置定稿时需要确定的规则

以下问题用于识别平台应当允许配置的内容，当前无需先为该企业确定答案或接入其 ERP。

1. **正式基线和职责。** 两版哪一版生效；谁对整笔业务负责；质管办与质检部的组织关系；特殊渠道如何签署。
2. **缺件结案。** 补齐、确认不再退回、核销、免退实物分别由谁批准，需要什么依据；0725 删除的判断支线由什么替代。
3. **处置粒度。** 同一申请、同一型号或同一到货批次能否拆分数量分别调拨、返修和报废；是否跟踪序列号；如何防止超量和重复处理。
4. **库存时点。** 原发货仓库、不合格库、不良品库、原料库和滞留库的实际含义及顺序；在哪一步计入现存量、可用量和排产参考量。不能仅凭流程图替财务或仓库确定入账规则。
5. **ERP 执行边界。** 各类单据在哪个系统制审；本平台负责创建、推送、人工登记还是只查询；失败、撤销和重复请求如何处理。
6. **核价和结案。** 价格来源、系数、运费分摊、承担方及审批后变更规则；缺件、库存执行、处置和损失处理完成到什么程度才能归档。
7. **退与换的完整范围。** 图中详细表达退回处理与质量损失，但换货补发、客户确认、退款等环节没有形成完整链路。它们是否由其他流程承担，需要明确后再纳入范围。
8. **新增字段含义。** “自由项强制完成”的实际对象、录入者和阻断条件需确认，不能直接转成一个通用必填开关。

## 通用平台的配置验收用例

可将“已退部分继续处理，缺件部分持续跟进”作为通用能力的一组配置测试，覆盖跨部门、同一业务多条进度、明细权限和结案依赖。测试中采用明确标注的假设值；这些值不构成企业正式流程决定。

下列数字为测试示例：申请退回 10 件，实际收到 7 件，缺件 3 件。已退 7 件进入检验和一种已确认的处置路径；缺件 3 件形成独立跟进任务。收到补退、获准核销或其他批准结果后，再按确认规则判断结案。该样例不预设允许免退或自动核销。

| 验收点 | 应观察到的结果 |
| --- | --- |
| 缺件分流 | 已退部分继续检验，缺件任务仍可见；整体进度不被误标完成 |
| 精确权限 | 仓库改清点字段、质检改检验字段、合同执行部改运费；绕过界面的越权请求仍被拒绝 |
| 并发与行身份 | 两人修改不同授权字段均保留；明细排序不会把检验或核价结果写到另一行；冲突有明确提示 |
| 问题更正 | 错型和原始单据错误可关联到相应明细，修正有历史；不得重复创建同一处理任务 |
| 跨单据追溯 | 从业务总览定位到货、检验、处置、损失以及 ERP 单据状态 |
| 外部失败 | ERP 请求失败后显示未完成和可重试原因；重复提交不生成重复外部单据，前提是接口具备相应去重或查询能力 |
| 核价协作 | 运费与物料核价可分别填写，按确定条件汇合；审批内容对应明确版本 |
| 结案控制 | 缺件、处置或必要单据未达成条件时不能归档；例外结案保留批准依据 |

还需用另一类业务配置（例如项目下多个交付任务与分别验收）验证复用性：数据名称、参与者、明细范围、节点绑定和完成条件通过配置变化，平台核心不增加退货、质检、仓库等专用判断。主干跨表依赖应通过关系和流程配置直接表达，不要求搭建者另写一组仅用于维持同一业务进度的数据同步触发器。

后续产出应是通用能力规格、配置交互和可复用的验收场景。已有前端验收义务继续保留；连接器使用明确的测试适配器验证成功、失败与重复请求，不因本案例自动开展企业 ERP 接入或专用应用开发。
